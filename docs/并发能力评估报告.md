# agent-framework 多用户高并发能力评估报告

> 评估目标：判断本项目能否作为「pip 安装即用的核心 SDK」部署在服务器上，支持多用户并发同步使用，且不同用户的 Agent 任务互不影响。
>
> 评估日期：2026-06-03

## 一、总体结论

**架构方向是对的，核心隔离模型成立，但要达到两个目标——「pip 安装即用的 SDK」+「服务器多用户高并发」——目前还差若干必须修复的缺口。**

- ✅ **per-user Agent 隔离 + `AgentPool`** 是正确的方案。`serving/pool.py` 顶部对「Agent 实例级共享状态」的分析非常到位。
- ✅ **无状态化重构（ContextVar 注入）做对了**：`todo_write` 用 `_current_session_dir`、子代理用 `_current_subagent_events`，在 `asyncio.gather` 下语义正确（每个 Task 创建时拷贝 context），跨用户、跨同批工具调用都能正确隔离。
- ✅ **LLM 客户端可安全共享**（`AsyncOpenAI` 协程安全）；内置工具已无模块级可变单例（`structured_output` 等均无状态）。
- ✅ **`Session` 可从 JSONL 恢复**，为「外部化状态、无状态重建」打下基础。

但是：**有 2 个 P0 级跨用户串扰隐患、若干 P1 健壮性缺陷，以及一组「作为库发布」的打包问题。** 现状更接近「单机演示可用」，距离「生产级高并发 SDK」还需要一轮针对性加固。

---

## 二、必须修复（P0：跨用户串扰 / 安全越权）

### P0-1　同一 `(user_id, session_id)` 的并发 `run()` 没有串行化

`AgentPool.acquire()`（`pool.py:290-323`）只有全局 `Semaphore` + 创建期 per-key 锁，**运行期没有 per-key 串行**。

后果：同一用户的两个请求会命中同一个缓存 Agent 实例，两个 `run()` 并发跑，同时改：
- `self._history._messages`（`history.py:77` append，无锁）→ 消息交叉错乱
- `self._session` 的 `conversation.jsonl`（`session.py:112` append）→ JSONL 行交叉
- `self._work_started` / `self._plan_created`（`agent.py:462`）→ 流程标记竞态

> ContextVar 本身没问题（各 Task 独立 context），坏的是 Agent 的实例可变字段。

**修复**：在 `_PoolEntry` 上加 `asyncio.Lock`，对同一 key 全程持锁串行；或 `active_count>0` 时排队 / 抛 `409 Busy`。

### P0-2　默认 `agent_factory` 共享同一个可变 `AgentConfig`，`set_mode()` 跨用户污染

- `_default_agent_factory`（`pool.py:347-354`）把同一个 `self._agent_config` 实例传给每个 Agent；
- `Agent.__init__` 不拷贝（`agent.py:144`）；
- `set_mode()` 原地改（`agent.py:262`）。

后果：用户 A 切到 `superwork`，所有用户的 Agent 模式同时变成 `superwork`——安全检查被集体绕过（越权风险）。

**修复**：默认 factory 用 `dataclasses.replace(self._agent_config)`，或 `Agent.__init__` 内部 copy config。

## 三、强烈建议修复（P1：高并发健壮性）

### P1-3　多 worker / 多机部署下 `AgentPool` 是进程内的
`uvicorn --workers N` 或多机时 pool 不跨进程共享 → 同一 `(user, session)` 落到不同进程的不同 Agent → 状态不一致。
**建议**：① 按 `user_id` sticky routing；或 ② 无状态化——每请求从 `Session`（JSONL）恢复历史、用完即弃，pool 仅做热缓存。`Session.load_messages()` 已具恢复能力，方案 ② 可行。

> **✅ 已处理（采用最简单直观方案）**：
> 1. **历史可恢复**：`Agent.__init__` 新增 `session_id` 参数；传入时使用确定性 Session 目录、且若日志已存在则自动 `load_from_session` 恢复历史。`AgentPool` 默认 factory 用 `_derive_session_id(user_id, session_id)` 派生确定性目录名。
>    - 顺带修复了一个**单 worker 下就存在的真 bug**：此前 Agent 用随机 session id 且不读盘，LRU/idle 淘汰或进程重启后历史必丢、并在 `.sessions` 留下孤儿日志。
> 2. **多 worker 部署指引**：推荐 **按 `user_id` 粘性路由**（nginx `ip_hash` / 一致性哈希）——同一用户恒定落到同一 worker，进程内 pool 的 entry 锁即可保证同会话串行，**无需分布式锁**。若需故障转移，再叠加共享会话存储（NFS/EFS）让另一 worker 能 `load` 历史。
> 3. 自定义 `agent_factory` 若也想要历史可恢复，需自行把派生的 `session_id` 透传给 `Agent(session_id=...)`。
> 4. 回归测试：`test_agent_restores_history_from_session`、`test_pool_restores_history_after_eviction`。

### P1-4　`auto` 模式的交互式确认会拖垮并发
服务端 `auto` 模式每个不安全工具都 `await on_confirm`（示例阻塞 30s Future）。这段时间 `Semaphore` 名额一直被占 → 等确认会话挤占 `max_concurrent_runs`。
**建议**：服务端默认 `superwork`/`talk`；或把"等待人工确认"移出 semaphore 占用区间。

### P1-5　MCP 是真正的内存与隔离瓶颈
每个 user Agent 自建 `MCPManager` + 3–5 子进程（15–50MB/Agent，重度 MCP 仅 ~240 并发用户）。
**建议**：共享一组 MCP 进程并把 `user_id` 透传给 server；或将常用 MCP 能力降级为无状态 HTTP 工具；lazy-connect + idle 回收设为默认。

### P1-6　`session_id` 自动生成有碰撞面 + 跨进程写无文件锁
`generate_id()` 仅 16 bit 随机（`session.py:307-313`）；多进程写同一 `.sessions/` 目录无 OS 级文件锁。

> **✅ 已处理**：
> 1. **防碰撞**：`generate_id()` 随机部分 16 bit → **64 bit**（`secrets.token_hex(8)`），同一秒百万级会话碰撞概率也可忽略。回归：`test_generate_id_no_collision_under_burst`（2 万次零碰撞）。
> 2. **写入健壮性**：写入收敛到单一 `_append_jsonl()`，加**独占文件锁**（POSIX `flock`，非 POSIX 优雅降级 no-op）+ `flush` 落盘；读端本就跳过半截/损坏行，无需读锁。
>    - 说明：框架是 async 单线程，**同进程写入本就被事件循环串行化、不交错**；`flock` 解决的是多 worker **跨进程**写同一文件的整行原子性（生产 Linux 生效）。配合 P1-3 的粘性路由，跨进程同会话写本就应被避免，`flock` 为额外兜底。

## 四、作为「pip 安装即用的库」的问题（P2）

### P2-7　`config/` 与 `skills/` 不随 wheel 发布
`pyproject.toml:28-29` 只打包 `src/agent_framework`。消费方安装后没有 `config/prompts/`、`config/mcp_servers.json`、`skills/`；示例全用仓库相对路径，库使用者无法复用。
**建议**：默认提示词/技能作为 package data 打进包内，并提供 API 返回内置路径。

### P2-8　导入即 `load_dotenv()` + 依赖 CWD 的默认路径
`providers/base.py:117`、`agent.py:398` 隐式 `load_dotenv()`；session 默认 `.sessions`、MCP 默认 `./config/mcp_servers.json`、技能自动扫描 `_SKILL_SEARCH_PATHS`——全部相对宿主 CWD。
**建议**：库内不隐式 `load_dotenv`、不扫描 CWD；路径走显式配置。

### P2-9　示例与重构脱节（残留死引用）
`examples/multi_user_chat.py:353` 的 `/plan` 仍引用已删除的 `agent._todo_manager` / `mgr.state.items` → 运行必抛 `AttributeError`。
**建议**：改为读 session 的 `plan.json`（`todo_read`），补一轮示例回归。

### P2-10　对外 API 面不齐整
`AgentPool` 未在顶层 `agent_framework/__init__.py` 导出；无根目录 README/Quickstart、无 `py.typed`、类型标注不完整。
**建议**：统一公开 SDK API、补 `py.typed` 与类型、补 Quickstart 文档。

## 五、优化项（P3）

- **观测性**：`get_stats()` 缺 per-run 时延、MCP 进程数、内存水位、排队/被拒计数。
- **背压**：`_evict_lru` 在全实例 active 时仅 `warning` 不淘汰（`pool.py:411`），叠加 semaphore 可能让新用户长时间静默等待。
- **历史/压缩并发**：`ConversationHistory`/`Compactor` 无并发保护——与 P0-1 同源。

## 六、改进优先级路线图

| 优先级 | 事项 | 影响 |
|---|---|---|
| **P0** | 同 key `run()` 串行化（entry 锁） | 消除跨用户/同会话数据串扰 |
| **P0** | 默认 factory 拷贝 `AgentConfig` | 消除 `set_mode` 越权 |
| **P1** | 服务端确认不占 semaphore / 默认非交互模式 | 保住并发吞吐 |
| **P1** | 多 worker 方案（sticky 或无状态恢复） | 支持水平扩展 |
| **P1** | MCP 共享/隔离策略 | 突破内存瓶颈 |
| **P2** | 配置/技能打进包 + 去除 CWD 依赖 + 修示例 | 真正"pip 装了能用" |
| **P3** | 指标、背压、文档 | 生产可运维 |

---

## 七、结论

架构能实现多用户并行高并发、互不影响；核心隔离与无状态化已做对一大半。但当前代码在「同会话并发」和「默认配置共享」两处仍会串扰，加上 MCP 内存瓶颈与打包缺陷。完成 P0+P1 后即可达到「中等并发、单机/sticky 多 worker 生产可用」；要做到「大规模高并发 SDK」，还需把 P1 的无状态恢复 + MCP 共享 + P2 打包一并落地。
