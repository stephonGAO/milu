# AgentPool 多用户并发压测报告（真实 API）

> 目标：用**真实 LLM API** 压测 `AgentPool` 在多用户并发下的吞吐、跨用户隔离、同会话串行化、过载背压与池不变量，验证前序 P0–P3 + P1-5 加固在真实链路下成立。
>
> 脚本：[`tests/stress_real_api.py`](../tests/stress_real_api.py)（独立运行，不入 pytest 默认集）
>
> 日期：2026-06-03

## 一、测试环境与方法

- **提供商/模型**：通义千问 `qwen-turbo`（流式，`max_tokens=24`，复读机系统提示）
- **被测对象**：`AgentPool` + 精简 `Agent`（无工具/元工具/技能，纯 LLM 往返，聚焦并发本身），`session_enabled=True`（落临时目录，顺带压会话持久化写入路径）
- **运行方式**：进程内直接驱动 `AgentPool`（不经 HTTP，排除网络框架干扰，直击并发核心）
- **三个阶段 + 全程不变量校验**：
  - **Phase A**：N 个用户并发，每用户串行 R 次请求 → 测吞吐 + **跨用户历史隔离**
  - **Phase B**：对同一 `(user, session)` 并发 5 个请求 → 验 **P0-1 串行化**（history 不丢不乱）
  - **Phase C**：`max_concurrent_runs=2` + `acquire_timeout=0.5s`，瞬时并发 12 → 验 **P3 背压**（`PoolBusyError` 优雅拒绝）
  - 全程断言池硬不变量：`active_entries ≤ max_agents`、`in_flight ≤ max_concurrent_runs`

## 二、运行配置与结果

| 配置 | 用户数 | 全局并发 | 请求总数 | 成功率 | 吞吐 | 时延 p50 / p95 / max |
|---|---|---|---|---|---|---|
| 轮次 1 | 20 | 10 | 40 | **100%** | **5.79 req/s** | 2.68s / 5.29s / 5.59s |
| 轮次 2 | 40 | 20 | 80 | **100%** | **8.41 req/s** | 3.36s / 5.33s / 8.75s |

| 维度 | 结果 | 说明 |

## 三、观察到的两个非阻塞小问题

1. ~~**`AgentDone.total_usage.total_tokens` 在 qwen-turbo 流式下回传 0**~~ —— **✅ 已修复**
   根因：Agent 在 `finish_reason=="stop"` 时立即 `break`，而 OpenAI 兼容流的 usage 在 `finish_reason` 之后的「仅含 usage、空 choices」收尾 chunk 里（`stream_options.include_usage=True`），提前 break 丢失了用量。修复：不再提前 break，把流读完（自然 `[DONE]` 结束，外层 `asyncio.timeout` 兜底）。复测 token 合计正常（如 20 请求 = 1220 tokens）。回归测试 `tests/test_agent_usage.py`。

2. **池侧 `run_p50_ms`/`run_p95_ms` 与 Phase A 实测时延口径不同**
   池指标统计的是 **handle 持有时长**——包含「只 `acquire` 内省、不调用 `run()`」的隔离校验调用（接近 0ms），因此被稀释（轮次 2 池侧 p50≈908ms，而 Phase A 实测 LLM 往返 p50≈3.36s）。这是设计上的语义（"占用名额时长"≠"LLM 往返时长"）。端到端时延以压测脚本实测值为准；如需池侧精确反映 LLM 时延，可在仅 `run()` 的调用上单独打点。

## 四、结论

- **核心结论**：在真实 API 下，`AgentPool` 的多用户并发**正确、隔离、稳定**——120 次请求零失败、零跨用户串味、同会话严格串行、过载优雅拒绝、池不变量始终成立。前序 P0-1（同会话串行）、P1-3（隔离/持久化）、P3（背压/指标）在真实链路得到验证。
- **吞吐天花板**主要由**单次 LLM 往返时延（~2–3s）与账号 RPS 限额**决定，而非框架——这正是 `AgentPool` 用 `max_concurrent_runs` 限流 + `acquire_timeout` 背压要管理的对象。要更高吞吐：调大并发上限（受 API 配额约束）、用更快模型，或横向扩展多实例 + 按 `user_id` 粘性路由。
- **可改进项**：补 token 用量遥测（问题 1）；如需更高并发画像，可加入 MCP 工具调用与 `shared_mcp` 的对照压测。
