# Agent 可观测性系统设计能力教程

> 这是一份**方法论教程**,不是 milu 的实现说明书。
> 目标:让你建立起独立的设计判断力——面对**任何** agent(或后端)系统,都能从规划到落地,自己判断**何时、如何、在哪里**设置监测,最终设计出一套完整的观测系统。
>
> 全文以"普适原理 + milu 具体代码印证"的方式展开:每条原理先讲可迁移的通用逻辑,再用 milu 已落地的代码佐证。milu 的实现细节另见 `docs/可观测性方案设计.md`。

---

## 总纲(先记住这一句)

> **可观测性 = 为"将来会被追问的问题"提前留下证据。**
> 一切取舍(埋什么、记多细、存哪、怎么读)都从那张"问题清单"倒推。

---

## 第 0 步:破误区——"监测"不等于"可观测性"

这是设计意识的起点。两者经常被混为一谈,但驱动的设计完全不同。

| | Monitoring(监控) | Observability(可观测性) |
|---|---|---|
| 回答的问题 | **已知的**:"它还活着吗?CPU 高吗?" | **未知的**:"它**为什么**这次绕了三圈才答?" |
| 何时设计 | 事前就知道要看什么,做好仪表盘 | 事后能对**已记录的数据**提出当初没预料的新问题 |
| 形态 | 阈值、告警、红绿灯 | 可钻取、可还原、可对比单次请求的全过程 |

**核心心法**:可观测性不是"把能记的都记下来",而是**让系统具备"事后被追问"的能力**。你今天不知道明天会出什么 bug,但好的埋点能让明天的你把今天那次运行**完整复盘**出来。

### Agent 为什么尤其需要它——四重黑箱

1. **非确定性**:同样输入,LLM 每次可能走不同路径,无法简单复现;
2. **多步因果链**:一次回答背后是"想 → 调工具 → 看结果 → 再想",错在哪一环肉眼看不见;
3. **隐性成本**:token 在悄悄烧钱,且子 agent 会放大;
4. **涌现性故障**:死循环、调错工具、参数幻觉,都不是单点异常,而是过程问题。

> **结论**:为 agent 做监测,本质是把那条看不见的"因果链"变得可还原。后面所有取舍都围着这句话转。

## 第 1 步:从"必须能回答的问题"倒推(设计的总驱动)

不要从"我能记什么"开始,要从"我将来会被追问什么"开始。Agent 系统逃不掉的追问归成 **6 类**,这就是你整个系统的需求清单:

| 类别 | 典型追问 | 决定了你要埋什么 |
|---|---|---|
| **行为/正确性** | 为什么调了这个工具?模型当时**到底看到了什么**(最终 prompt)?为什么停下? | 工具名、参数、finish_reason、最终消息 |
| **性能** | 时间花哪了?首字多久(TTFT)?是模型慢还是工具慢? | 每段耗时、TTFT、按类别分解的时间 |
| **成本** | 烧了多少 token、在哪烧的、折多少钱、**含子 agent 吗**? | usage 增量、按 generation 求和、单价表 |
| **可靠性** | 工具报错没?安全判定拦了啥?fail-open 兜底触发没? | 状态码、judge 裁决+理由、fail_open 标记 |
| **可比较** | 这次比上次更快/更贵/更好吗?有没有退化? | 可聚合的运行索引(每次一行汇总) |
| **可追溯/审计** | 给定这条输出,还原**完整**因果链:谁、做了什么、何时 | trace_id 串起的整棵树 + 时间戳 |

> **最重要的设计纪律:埋点要"倒着"做。** 不是"这里好埋就埋",而是"将来要回答 X,所以这里必须留下证据"。
>
> milu 的 slogan——"可解释、可测量、可比较、可追溯、可视化"——正是这 6 类问题的浓缩。给自己的系统也先写出这张表,后面就不会盲埋或漏埋。

## 第 2 步:三大支柱,以及 Agent 的特殊形状

业界把可观测性数据分三种("three pillars"),各有取舍:

- **Logs(日志)**:离散事件,细节最全,但散落、难关联。回答"这一刻发生了什么"。
- **Metrics(指标)**:聚合后的数字(计数、分位数),极便宜,适合仪表盘和告警,但**丢失单次细节**。回答"整体趋势如何"。
- **Traces(追踪)**:**单次请求**跨组件的因果+时间树。回答"这一次,从头到尾经过了什么"。

**对 agent,trace 是王。** 因为 agent 的价值和故障都在那条因果链上。而且另外两者可由 trace 派生:

- 指标 = 把很多 trace **聚合**;
- 日志 = trace 里的 **span event**(某时刻的点事件)。

> **设计选择**:milu 不搭三套系统,而是**以 span 树为唯一底座**,指标和事件从它长出来。
> **先把 trace 做扎实,指标和日志几乎是免费的副产品。**

## 第 3 步:核心心智模型——一次运行 = 一棵 Span 树

把这个模型刻进脑子,后面全靠它。

- **Span(跨度)= 一个有起止的"工作单元"**,带:名字、种类(kind)、开始/结束时间、属性(attributes)、点事件(events)、父指针(parent_id)。
- **Trace(追踪)= 共享同一个 trace_id 的所有 span**,靠 parent_id 串成一棵**树**。

为什么"树"天然适配 agent?因为 agent 的执行结构**本身就是树**:

```
invoke_agent                      ← 根:整次 run()
├─ chat {model}        (turn 1)   ← 一次 LLM 调用 (generation)
├─ execute_tool: web_search       ← 一个工具
├─ guardrail: judge               ← 安全判定
├─ blocked_on_user                ← 等人审批
├─ chat {model}        (turn 2)
│   └─ execute_tool: 子agent调用
│       └─ invoke_agent           ← 子 agent 整棵树嵌在这里!
│           ├─ chat {model}
│           └─ execute_tool: ...
└─ compact                        ← 上下文压缩
```

**milu 印证**:`tracer.py` 中 span 的层级**不是手动传 parent**,而是用 **ContextVar**(`_current_span`)——进入一个 span 就把它设为"当前",其内部新建的 span 自动认它当父。子 agent 沿 asyncio 任务树天然继承父 tracer,所以**子 agent 的整棵树零代码就挂到父的 `execute_tool` 下**。这就是"委派链路可追溯"的实现秘密。

> **设计启示**:当执行有"嵌套/委派"结构时,**用上下文传播(进程内 ContextVar / 跨进程 W3C traceparent header)而非手动穿参**。手动穿 parent 会污染每个函数签名,且子调用一深就漏。

**span 的 kind(种类)为什么重要?** milu 定义了 `invoke_agent / chat(generation) / execute_tool(tool) / guardrail / blocked_on_user / compact`。分类不是好看——它让你能**按类别聚合、着色、推理**:"所有 generation 的 token 求和 = 成本"、"所有 tool 耗时求和 = 工具时间"、瀑布图按 kind 上色。**没有分类,聚合无从下手。**

## 第 4 步:【判断力核心 ①】粒度决策——span / 属性 / 事件 / 不记,怎么选?

这是"怎么知道在**哪里**该埋"的正面回答。一套可直接套用的判断规则:

**① 给它一个 Span,当——**
它是一个**有意义时长**、你将来想**独立测量/定位/对比**的工作单元;尤其当它**可能有子级**或**会独立失败**时。
→ milu:一次 LLM 调用、一次工具执行、一次 judge 判定、整次 run、一次 compaction。都满足"耗时 + 可独立失败 + 想单独看"。

**② 给它一个 Attribute(属性),当——**
它是某个 span 的**性质或度量**(标量或小结构),用来描述"这次工作是什么样"。
→ milu:`gen_ai.request.model`、`usage.input_tokens`、`finish_reasons`、工具名、工具参数、judge 三态裁决。
→ **注意 TTFT 做成属性**(`time_to_first_chunk`)而非事件——它是这次 chat 的一个度量值,不需要在时间轴上单独定位。

**③ 给它一个 Event(点事件),当——**
它是 span **内部某一时刻**发生、本身无时长、但你想要**时间戳**的事。
→ 例:"发生一次重试"、"流式第一个 chunk 到了"。事件是"日志"在 trace 里的归宿。

**④ 什么都不记,当——**
它**高频、低信息、或可派生**。
→ 最典型:**不要给每个流式 chunk 建 span 或事件**,否则被淹没。你记"首 chunk 时刻(TTFT)+ 总 chunk 数",而不是每个 chunk。

> **口诀**:**有时长且想独立看 → span;描述这段工作的值 → 属性;某一刻的点 → 事件;高频可派生 → 丢掉。**

**基数(cardinality)纪律**也在这一步:别把**无界的唯一值**塞进将来要"分组聚合"的维度。user_id 有几百万个——它适合放进 span(用于过滤/还原单次),但**不适合**当指标的聚合维度(否则指标爆炸)。milu 的做法:user_id 进 span 和"按用户分文件",但聚合(p50/p95)在**单用户文件内**或全量上算,不拿 user_id 当聚合键。

## 第 5 步:【判断力核心 ②】找到"盲窗"和"被错记的时间"

这是从"能用"到"好用"的两个高阶意识,也是 milu 真实踩过、专门修过的点。

### 盲窗(silent window):时间在流逝,但外部观察不到任何信号

milu 发现 agent 有两段"静默":正文输出结束 → 工具参数还在流式生成完、以及 judge 阻塞式判定调用期间——这两段对消费者是**零事件**的,看起来像卡死。于是补了两个状态信号事件 `ToolCallPreparing` 和 `SafetyCheckStart`(见 `events.py`),专门覆盖这俩窗口。

> **设计启示**:主动问自己——"系统有没有哪段时间在干活、却什么都没发出来?"
> **凡是'有耗时但无信号'的缝隙,都是该补埋点的地方。** 这能让 trace 不留黑段。

### 时间归因(time attribution):把时间记到**正确的**原因头上

milu 专门拆了 `blocked_on_user` span,把"等人审批"的时间从工具耗时里**剥离**。为什么?一个需要人工确认的工具,若把"等了用户 5 分钟"算进执行时间,它会显得**慢得离谱**,你会误判成工具性能问题——实际是人在喝咖啡。

> **设计启示**:**机器时间和人等待时间必须分开;网络等待、排队等待、真正计算,能分则分。**
> 时间分解错了,所有性能结论都会被带偏。milu 的 `RunReport` 因此把时间拆成 `llm_time / tool_time / judge_time / wait_time` 四份。

这两条是"高手意识",决定了监测到底**能不能指向真正的根因**。

## 第 6 步:横切设计原则(非功能需求)——监测自己绝不能成为故障源

埋点是"横切关注点",会渗进每个角落,所以工程纪律比业务代码更高。

1. **Fail-silent / fail-open——监测出错,业务无感。**
   sink 写盘失败?只记一条 warning,**绝不**让它冒泡打断 `agent.run()`。这与 milu 安全判定器的 fail-open 同源:**增强网,不是硬门槛。** 宁可丢一条 trace,也不能因记日志把对话搞崩。

2. **关闭时零开销 + 不穿参。**
   `Agent(trace=False)`(库默认)走 `NOOP_TRACER` / `NOOP_SPAN`,埋点调用变空操作,基本零成本。靠 ContextVar 注入当前 tracer,**埋点是"包裹式"的——不改控制流、不污染函数签名**。读 `agent.py` 会看到埋点是把原逻辑 `with span:` 包起来,而非加 if/else 分支。

3. **库默认关、应用默认开。**
   作为库被集成时默认关(单测 hermetic、不偷偷落盘、不惊讶集成方);CLI/Web 这种**应用**入口默认开(部署就是要数据)。milu 的 memory/knowledge/trace 全遵循此约定。

4. **内容捕获策略(capture policy)要可调。**
   prompt 和输出可能极大、且含 PII。milu 给 `full / truncated / none` 三档,默认 `truncated` 截 2000 字。**这是隐私、体积、可用性的三方平衡**:全留太大也可能违规,全不留又没法复盘行为。让它**可配置**,把决定权交给部署方。

5. **传播机制选对。**
   进程内用 ContextVar;跨进程(微服务、子进程)用 **W3C traceparent header** 把 trace_id/parent 传过去。milu 现为进程内,但 ID 格式已按 W3C(见第 7 步),将来跨进程零改造。

## 第 7 步:对齐标准、面向未来——为什么自研也要"说标准话"

milu 完全是自研 JSONL,**为什么还要对齐 OpenTelemetry?**

因为**标准是一份"对未来的期权"**。你今天用自研格式落盘,明天要"接到 Langfuse / OTLP 后端去",如果属性名一开始就叫 `gen_ai.usage.input_tokens`(OTel GenAI semconv v1.37+ 标准名),那一天**导出几乎零映射**;如果当初随手叫 `tokens_in`,就得写翻译层、还容易翻错。

milu 的具体做法,可当模板:

- **属性名**对齐 OTel GenAI 新语义:`gen_ai.provider.name`、`gen_ai.usage.input_tokens/output_tokens`、`gen_ai.response.finish_reasons`、`gen_ai.tool.name`……**废弃名一律不用**;
- **自有概念**(标准没覆盖的,如 fail_open、判定理由)走私有命名空间 `milu.*`——既不污染标准,又一眼能区分;
- **ID 格式**按 **W3C Trace Context**:trace_id 32 hex、span_id 16 hex(`secrets.token_hex`),天然可跨系统对接;
- **每行带 `schema` 版本号**(`SCHEMA_VERSION`)。**你的格式一定会演进**,带版本号,老数据将来还能被正确解读、迁移逻辑也有依据。

> **设计启示**:**优先采用领域已有的标准词汇表,哪怕你自己存。**
> 自创术语是技术债;对齐标准是把"将来换后端/接生态"的成本提前降到接近零。

## 第 8 步:存储与生命周期——让数据"存得下、读得快、不爆炸"

trace 数据是**只增的洪流**,存储设计直接决定系统能否长期运行。milu 的几条都是可复用套路:

1. **Append-only(只追加)抗崩溃。** span 一结束就 append 一行 JSONL。进程崩了,已写的行还在、不会损坏整文件。

2. **读时跳过坏行(skip-bad-line)抗损坏。** 某行写到一半进程挂了,读取时跳过这一行而非整文件报废。**只增 + 容错读 = 崩溃韧性**,到处用得上。

3. **按实体分区(partition)= 隔离 + 读取有界。** trace 索引按 `runs/{safe_user_id}.jsonl` 分文件。好处双份:Web 多用户**只读自己那份**(隐私隔离 + 不被别人数据拖慢);单文件天然有界。`{safe_user_id}` 清洗约定 memory/scheduler/knowledge 共用——**一致性本身就是可维护性。**

4. **轮转 + 保留上限,防无限增长。** 运行索引每份超 `RUNS_INDEX_MAX_LINES`(5000)就原子重写丢最旧;trace 明细按 `retention_days` 过期清理。**任何"永久追加"的文件都必须有天花板**,否则迟早"越读越慢"。

5. **【架构关键】索引与明细分离——目录 vs 正文。** 最值得学的一招:一次运行落**两处**——
   - **轻量索引**:`runs/{user}.jsonl`,每次运行**一行汇总**(`RunReport`:耗时、token、成本、错误数……);
   - **重型明细**:`{session}/trace.jsonl`,这一次的**整棵 span 树**。

   你**扫索引**(便宜、行少)找到想看的那次,再**只打开那一个明细文件**钻取。`milu trace list` 读索引,`trace show <id>` 才读明细。
   > **把"目录"和"内容"分开,是所有大规模可观测系统的通用骨架**——别让"看一眼列表"被迫加载所有细节。

## 第 9 步:从数据到洞察——没人看得懂的数据等于没有

埋点只是原料;**让人(和你自己)能据此判断**才是目的。消费层要回扣第 1 步那 6 类问题。

### 关键概念:聚合(Aggregation)

**单次 trace** 回答"**这一次**发生了什么";但你常想知道"**整体上**怎么样"——这就需要把**很多次运行的数据合并成几个概括性数字**,这个动作就是聚合。

milu 的 `milu trace stats` 会把最近几十/几百次运行**揉到一起**算出:总次数、平均耗时、token/成本总和、工具调用与出错次数、以及**耗时的 p50 / p95**。

> 一句话:**聚合 = 把"一堆单次记录"压缩成"少量概括指标"。**
> 这也呼应第 2 步——**指标(metrics)本质就是对 traces 做聚合的产物。**

### 关键概念:p50 / p95(分位数,Percentile)

衡量"耗时分布"最常用的两个数字。

- **p50**:第 50 百分位 = **中位数**。所有运行耗时**从小到大排队**,正中间那个。意思是"**一半请求比它快,一半比它慢**"。
- **p95**:第 95 百分位。排好队站在 **95% 位置**那个。意思是"**95% 请求都比它快,只有最慢的 5% 比它还慢**"。

**为什么不用平均值?——平均值会撒谎。** 用一组数据感受(10 次运行,耗时秒,已排序):

```
1, 1, 1, 1, 1, 1, 1, 1, 1, 100
```

| 指标 | 值 | 它在说什么 |
|---|---|---|
| **平均值** | **10.9 秒** | 😱 看着像"普遍很慢"——被极端值带偏 |
| **p50(中位数)** | **1 秒** | ✅ "典型体验其实 1 秒" |
| **p95** | **~1 秒** | ✅ "绝大多数都很快" |
| **最大值 / p100** | **100 秒** | ⚠️ "但有一次惨案" |

9 次都是 1 秒,只有 1 次卡了 100 秒:平均值 10.9 会让你误判"系统普遍慢";而 p50=1 诚实地说"典型 1 秒",那次惨案则在 p95/p99 或最大值里暴露。

那"最倒霉的 5%"叫**长尾(long tail)**——恰恰是用户**真正会抱怨、会流失**的部分。平均值把长尾稀释藏起来;分位数专门把它揪出来。

> **专业做法是两个一起看**:
> **p50 = 大多数人的真实体验;p95/p99 = 最倒霉少数人有多惨。**

**怎么读 milu 的 stats**:看到 `耗时 p50=1.2s p95=8.7s`,解读为——典型一次对话 1.2 秒答完(不错);但**有 5% 的对话要 8.7 秒以上**,值得 `trace show` 点开看是哪个工具慢、还是 LLM 卡了、还是在等人审批(这正是第 5 步把 `blocked_on_user` 拆出来的价值:这一步能分清"真慢还是在等人")。

### 其余消费视图(每个都回扣第 1 步的问题)

- **列表(list)**:一眼扫所有运行——回答"可比较"。
- **瀑布图(waterfall)**:按时间轴铺开 span,长度=耗时——**一眼看出时间花在哪**,回答"性能"。按 kind 上色,judge 理由直接展示(它最不直观,最该被看见)。
- **对比(compare)**:两次运行并排,看回归。
- **成本(cost)**:milu 学 Langfuse **双轨制**——token 用**真实 usage**,单价查表(`pricing.py`,最长前缀匹配),**查不到就 `cost=None`,绝不瞎算**。
  > 职业操守:**宁可显示"未知",不可编造数字**;且 token 求和要**含子 agent**(`build_run_report` 按所有 generation span 求和),否则成本被严重低估。
- **预聚合**:`RunReport` 在运行结束时就把常见汇总算好存进索引,常见追问 O(1) 命中,不必每次重扫整棵树。

> **设计启示**:**消费层每个视图,都应能对应回"必须能回答的某个问题"。**
> 做不出对应问题的视图就是花架子;答不上的问题就是缺的视图。

### 心智图

```
很多次运行 (一堆 trace)
        │
        │  ← 聚合(aggregation)
        ▼
   少量概括指标
        ├─ 总次数 / 总成本        ← 求和、计数
        ├─ p50 耗时  = 典型体验    ← 分位数
        └─ p95 耗时  = 长尾惨案    ← 分位数(揪出被平均值藏起来的慢请求)
```

## 第 10 步:可复用的"设计 Checklist"

下次面对任何 agent(或任何系统)要从零设计监测,按这十问走一遍:

1. **列问题**:将来必须能回答哪些追问?(行为 / 性能 / 成本 / 可靠性 / 可比较 / 审计)
2. **画树**:把系统执行画成"工作单元的嵌套树"——这些就是 span 候选。
3. **定粒度**:每个单元逐一判 span / 属性 / 事件 / 丢掉(用第 4 步口诀);检查基数纪律。
4. **补盲窗、正归因**:哪段"有耗时无信号"?哪段时间被记错了主?(第 5 步)
5. **对标准**:选 OTel GenAI 这类标准词汇表,把属性映上去;ID 用 W3C;**每行带 schema 版本**。
6. **定横切策略**:fail-silent、关闭零开销、内容捕获档位、隐私、传播(ContextVar / traceparent)。
7. **定存储**:append-only + 跳坏行;选分区键;定轮转/保留上限;**索引与明细分离**。
8. **建消费层**:列表 / 瀑布 / 聚合(p50/p95)/ 对比 / 成本——每个都回扣第 1 步的问题。
9. **可验证**:写测试守住不变量——结构正确、并发隔离、fail-silent、**关闭时零产物**。(milu `tests/test_trace.py` 正是按这几条组织)
10. **迭代**:每当线上出现"这个问题我答不上来",那就是一处埋点缺口——补上,系统就进化一次。

## 一页速查(钉在墙上版)

| 维度 | 一句话原则 |
|---|---|
| **目的** | 为"将来会被追问的问题"提前留证据 |
| **驱动** | 从 6 类问题倒推埋点,不是从"能记什么"正推 |
| **模型** | 一次运行 = 一棵 span 树;委派靠上下文传播,不穿参 |
| **粒度** | 有时长想独立看→span;描述值→属性;某一刻→事件;高频可派生→丢 |
| **盲点** | 补"有耗时无信号"的盲窗;把人等待时间从机器时间里剥离 |
| **纪律** | fail-silent、关闭零开销、内容可调、控制基数 |
| **标准** | 用 OTel GenAI 词汇 + W3C ID + schema 版本,换后端零映射 |
| **存储** | append-only + 跳坏行 + 分区 + 轮转 + 索引/明细分离 |
| **洞察** | 看 p50(典型)+ p95(长尾),别信平均值;成本查不到就标未知 |
| **演进** | 答不上的问题 = 缺的埋点,持续迭代 |
