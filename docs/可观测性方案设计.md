# milu Agent 可观测性方案设计（Observability / Tracing）

> 状态：v2 修订稿（已融入业界调研结论），经评审后实施。
> 目标：解决 Agent 运行黑箱问题，让每一次 `Agent.run()` **可解释、可测量、可比较、可追溯、可视化**。

---

## 1. 问题与现状

一次 `Agent.run()` 内部发生的事远多于事件流暴露的内容，且事件流消费完即消失：

| 内部环节 | 黑箱点 |
|---|---|
| LLM 流式调用 | 每次调用的耗时、首 token 延迟（TTFT）、单次 usage、finish_reason 无处沉淀 |
| AI 安全判定（judge） | **三态裁决结果、理由、fail-open 是否发生完全不可见** —— 最需要"可解释"的环节 |
| 人工审批 | 等待人工确认的时长与决策混在整体耗时里，无法区分"模型慢"与"人慢" |
| 工具执行 | 单工具耗时、参数、并发批次关系不可见 |
| 上下文压缩 | 压缩策略、省了多少消息、摘要调用开销不可见 |
| 子代理 | 内部过程数据用完即弃，无法事后下钻 |
| 整次运行 | 无持久化运行记录，无法事后分析/对比 |

已有地基（复用，不重复造轮子）：`StreamChunk.usage` 已逐 chunk 累积；`AgentEvent` 体系已覆盖"发生了什么"；Session 的 append-only JSONL + 按 (user, session) 隔离；ContextVar per-run 注入模式；Web SSE 通道与五面板前端；`AgentPool.get_stats()` 统计先例。

**缺的不是数据源，而是一条把数据"结构化 → 沉淀 → 聚合 → 展示"的流水线。**

## 2. 业界调研结论（2026-06，三路并行调研）

调研对象：Langfuse、LangSmith、OTel GenAI semantic conventions、OpenInference/Phoenix、OpenLLMetry、OpenAI Agents SDK、Claude Code 遥测、CrewAI、AutoGen/Semantic Kernel、Google ADK、Pydantic AI/Logfire、AgentOps、W&B Weave。

**结论一：Trace/Span 嵌套树是无争议的业界共识。** 所有平台都用"一次执行 = 一棵 span 树"建模 Agent 循环；Langfuse 有专门的 `agent`/`tool`/`generation`/`guardrail`/`evaluator` observation 类型，OpenAI Agents SDK 有 `agent_span`/`generation_span`/`function_span`/`guardrail_span`，Claude Code 是 `interaction → llm_request / tool → 子代理嵌套`。子代理一律嵌套挂在父工具 span 之下。

**结论二：OTel GenAI semantic conventions 是事实标准，但仍在演进（Development 状态）。** v1.37.0 是分水岭：`gen_ai.provider.name` 取代 `gen_ai.system`、`gen_ai.usage.input_tokens/output_tokens` 取代 `prompt_tokens/completion_tokens`、消息全文回归结构化 span 属性（`gen_ai.input.messages` 的 `{role, parts[]}` JSON Schema）。Langfuse 与 LangSmith **都原生 ingest OTLP** 并做了 GenAI semconv 映射——一份 OTLP 输出可通吃 Langfuse / LangSmith / Phoenix / Jaeger。W3C Trace Context 要求 trace_id 32 hex / span_id 16 hex。

**结论三：默认开关呈清晰二分法。** 数据留在本地/自家后端的默认开（OpenAI SDK、AutoGen）；数据离开本机的一律 opt-in（Claude Code 全关、Pydantic AI 默认关、ADK 云导出显式开）。规范明文：消息全文 "SHOULD NOT capture by default"。

**结论四：轻量框架的正确姿势是"自有轻量模型 + 属性名对齐 OTel + OTLP 仅作可选导出"。** OpenAI Agents SDK 与 Claude Code 都不依赖 OTel SDK 作为内核（Claude Code 双写 `gen_ai.*` 属性）；Pydantic AI 走纯 OTel 但因此绑定 OTel API。对 milu（零重依赖定位）取前者。Phoenix（pip 装完 `phoenix serve` 即起、SQLite、本地 OTLP collector + UI）证明 local-first 形态成立。

**结论五：框架自带本地 trace 查看器是被验证的强需求，且是市场空白。** Google ADK 的 `adk web` dev UI（Trace + Events 双视图）、AgentOps 的瀑布图/会话回放是体验标杆；但**没有任何轻量框架同时做到"本地优先 + 内置 UI + trace 查看器"**——milu 的 `milu serve` 加第六面板正好卡进这个空白。

**对 v1 设计稿的修订点**（其余骨架不变）：

1. 属性名全面对齐 OTel GenAI v1.37+ 新名（详见 §3.3），废弃名（`gen_ai.system`、`prompt_tokens` 等）一律不用；
2. ID 采用 W3C 格式：trace_id 32 hex、span_id 16 hex（`secrets.token_hex`），将来 OTLP 导出零映射；
3. **取消 `agent.turn` 中间层 span**，改为每个 span 带 `milu.round` 属性——对齐 Claude Code/OTel 的扁平结构（llm/tool 直接挂根），瀑布图更干净，轮次分组由属性承担；
4. **新增 `blocked_on_user` 审批等待 span**（学 Claude Code）：把"等人"的时长从工具耗时中剥离，并记录决策（approved/rejected）与来源；
5. span kind 体系对齐 Langfuse/OpenAI SDK：`agent` / `generation` / `tool` / `guardrail`（judge）/ `confirmation` / `compaction`，将来对接外部平台类型零翻译；
6. 成本计算取 Langfuse 双轨制：真实 usage 优先，价格表估算兜底，**查不到价格 cost=None 绝不瞎算**；价格表 config 可覆盖（内置表重点覆盖国内厂商是 milu 差异化点，但出厂值标注"示例价，建议覆盖"）；
7. 每行 JSONL 带 `schema` 版本字段——GenAI semconv 仍在破坏性演进，内部存储与导出映射解耦，约定变了只改导出层；
8. 内容捕获分级 `capture_content: truncated(默认)/full/none`；本地落盘可宽松，**OTLP 外发路径默认脱敏**（spec 要求）；
9. Sink 可插拔，支持"追加"与"整体替换"两种装配（学 OpenAI SDK 的 add/set processors）。

## 3. 总体设计

### 3.1 核心抽象：一次 `Agent.run()` = 一棵 span 树

```
trace (trace_id 32hex)
└── invoke_agent                        ← 根：provider/model/mode/输入摘要/聚合 usage/成本
    ├── chat deepseek-chat   (round 1)  ← TTFT/usage/finish_reasons
    ├── guardrail judge      (round 1)  ← 送判工具/三态裁决+理由/fail_open
    ├── blocked_on_user shell_command   ← 审批等待时长 + 决策（仅 confirm 路径）
    ├── execute_tool shell_command (round 1)
    ├── execute_tool researcher    (round 1)   ← 子代理工具
    │   └── invoke_agent                ← 子代理整棵树自动嵌套（ContextVar 继承）
    │       ├── chat deepseek-chat
    │       └── execute_tool web_search
    ├── compact                         ← 触发压缩时才有
    └── chat deepseek-chat   (round 2)  ← final
```

### 3.2 数据模型（`@dataclass`，与项目风格一致）

```python
@dataclass
class Span:
    trace_id: str            # 32 hex（W3C Trace Context）
    span_id: str             # 16 hex
    parent_id: str | None    # None = 根
    name: str                # "invoke_agent" | "chat {model}" | "execute_tool {tool}" |
                             # "guardrail judge" | "blocked_on_user {tool}" | "compact"
    kind: str                # agent | generation | tool | guardrail | confirmation | compaction
    start_time: float        # epoch 秒（墙钟，展示用）
    end_time: float | None
    duration_ms: float | None  # monotonic 差值（精确计时）
    status: str              # "ok" | "error"
    attributes: dict         # OTel gen_ai.* 对齐属性 + milu.* 私有命名空间
    events: list[dict]       # span 内时间点，如 {"name": "first_token", "offset_ms": 420}
```

JSONL 落盘时每行附加 `"schema": 1`。

### 3.3 属性对齐表（OTel GenAI v1.37+ 命名；milu 私有信息走 `milu.*`）

| Span | name / kind | 关键属性 |
|---|---|---|
| 根 / 子代理 | `invoke_agent` / agent | `gen_ai.operation.name=invoke_agent`、`gen_ai.provider.name`（qwen/deepseek/anthropic…，官方枚举外用自定义小写值）、`gen_ai.request.model`、`gen_ai.conversation.id`←session_id、`gen_ai.agent.name`（子代理为其工具名）、`milu.mode`、`milu.user_input`（按捕获级别）、聚合：`gen_ai.usage.input_tokens/output_tokens`、`milu.turn_count`、`milu.tool_calls`、`milu.cost_estimate`、`error.type` |
| LLM 调用 | `chat {model}` / generation | `gen_ai.operation.name=chat`、`gen_ai.request.model`、`gen_ai.usage.input_tokens/output_tokens`（本次调用增量）、`gen_ai.response.finish_reasons`（数组）、`gen_ai.response.time_to_first_chunk`（秒，OTel 单位）、`milu.round`、`milu.message_count`、`milu.reasoning_tokens` |
| 工具执行 | `execute_tool {tool}` / tool | `gen_ai.tool.name`、`gen_ai.tool.call.id`、`gen_ai.tool.type=function`、`gen_ai.tool.call.arguments`（按捕获级别截断）、`milu.round`、`milu.output_len`、`error.type` |
| AI 安全判定 | `guardrail judge` / guardrail | `milu.judge.tools`（送判名单）、`milu.judge.model`、`milu.judge.verdicts`=[{tool,id,decision,reason}]、**`milu.judge.fail_open`**（判定失败回退执行，最需被审计的路径） |
| 审批等待 | `blocked_on_user {tool}` / confirmation | `gen_ai.tool.name`、`gen_ai.tool.call.id`、`milu.decision`（approved/rejected）、`milu.message`（用户指示，按捕获级别）；duration 即等待时长 |
| 压缩 | `compact` / compaction | `milu.compact.strategy`（auto/reactive/manual）、`milu.compact.before/after`（消息数） |

### 3.4 关键设计决策

1. **Tracer 经 ContextVar 注入，与 judge/todo 同模式**。`run()` 入口检查 `_current_tracer`：空 → 顶层运行，新建 Trace + JSONL sink；已有 → 子代理运行（沿 asyncio 任务树自动继承），把自己的 `invoke_agent` span 挂在当前活动 span（父的 `execute_tool` span）下。委派链路零额外代码完整可追溯。`_current_span` 同样走 ContextVar——工具批次经 `asyncio.gather` 各自在任务级 Context 中设置自己的 span，并发隔离天然成立。
2. **fail-silent**：所有 sink 写入包 try/except 只记 warning——与 judge 的 fail-open 哲学一致，观测绝不影响业务。
3. **关闭时零开销**：`Agent(trace=False)`（库默认）得 NoopTracer，埋点全部空操作，单测 hermetic。**CLI/Web 按 config.json `observability.enabled`（默认 true）开启**——与 knowledge"库默认关、应用层默认开"先例一致；这同时符合业界"本地落盘默认开、网络外发默认关"的二分法。
4. **存储跟随 Session**（写数据锚定 `user_data_dir()` 约束）：有 session → `{session_dir}/{id}/trace.jsonl`（与 conversation.jsonl 并排，round 号互相关联）；无 session → `~/.milu/traces/{trace_id}.jsonl`。运行索引 `~/.milu/runs.jsonl` 每次顶层运行结束追加一行 RunReport。保留策略 `retention_days`（默认 30），应用层启动时顺带清理。
5. **span 结束即 append 一行 JSONL**（与 session.py 同款）：崩溃不丢已完成 span，半途运行可追溯到中断点——这本身就是排障价值。未完成的 span（如压缩未发生）不落盘。
6. **Sink 可插拔**：`TraceConfig.extra_sinks` 追加（如 Web 层 CallbackSink 喂 SSE）、`sinks` 整体替换；OTLP exporter 是 P4 的一个可选 sink（`milu[otel]` extra，仿 ddgs 延迟导入）。

### 3.5 模块布局

```
src/milu/observability/
├── __init__.py     # 导出 TraceConfig / Tracer / Span / RunReport 等
├── span.py         # Span dataclass + W3C ID 生成 + 内容截断工具
├── tracer.py       # Tracer / NoopTracer / TraceConfig / ContextVar（_current_tracer/_current_span）
├── sink.py         # TraceSink 协议 + JsonlSink + CallbackSink
├── report.py       # RunReport 聚合 + runs.jsonl 索引读写 + 保留期清理

```

## 5. RunReport（可测量、可比较的载体）

顶层运行结束由 span 树聚合，追加到 `~/.milu/runs.jsonl`：

```python
@dataclass
class RunReport:
    trace_id: str; started_at: float
    provider: str; model: str; mode: str
    session_id: str | None; user_id: str | None
    status: str                  # "ok" | "error:<type>" | "interrupted"
    duration_ms: float; turn_count: int
    input_tokens: int; output_tokens: int; reasoning_tokens: int
    cost_estimate: float | None; cost_currency: str | None   # 查不到价格 = None，不瞎算
    ttft_ms: float | None        # 首轮首 token 延迟
    llm_time_ms: float; tool_time_ms: float
    judge_time_ms: float; wait_time_ms: float   # 时间分解："时间花在哪"一目了然
    tool_calls: int; tool_errors: int
    judge_denies: int; judge_confirms: int; fail_opens: int
    compactions: int; subagent_runs: int
```

成本（`pricing.py`，学 Langfuse 双轨制）：token 一律用 provider 返回的真实 usage；单价查表——config.json `observability.price_table`（按模型名前缀匹配）优先于内置表；查不到 → `cost_estimate=None`，展示层标"未配置价格"。内置表出厂仅含少量示例条目并注明可能过期，鼓励覆盖。

对比（P2 `compare`）：输入 N 个 trace_id 或筛选条件，输出对齐表格（耗时/token/成本/轮数/工具/时间分解，差值与百分比）。后续可衔接 `tests/benchmark_agent.py` 固定任务集跨厂商评测（沿用 knowledge benchmark 的"评测 → docs 报告"模式）。

## 6. 接口与配置

```python
Agent(llm)                              # trace=False，库默认关闭（hermetic）
Agent(llm, trace=True)                  # 开启，默认配置
Agent(llm, trace=TraceConfig(capture_content="full", extra_sinks=[...]))
```

config.json 新增分节（按 scheduler/knowledge 模式接入，`_builtin_defaults()` 从 TraceConfig 派生）：

```json
{
  "observability": {
    "//": "Agent 运行追踪。CLI/Web 默认开启（本地落盘）；库内直接构造 Agent 默认关闭",
    "enabled": true,
    "capture_content": "truncated",
    "max_content_chars": 2000,
    "retention_days": 30,
    "price_table": {}
  }
}
```

CLI `build_agent` / Web `create_app` 显式读配置下传 TraceConfig，**不侵入**裸 `Agent(llm)` 构造（库纯净性）。

## 8. Web 观测面板（P3）

端点：`GET /api/traces?limit=20`（运行列表，按 X-User-Id 过滤）、`GET /api/trace/{trace_id}`（完整 span 树）、`GET /api/observability/summary`（聚合卡片）。

前端（vanilla JS、无 CDN、CSS 图表约束不变）第六面板「观测」：运行列表 → 点击下钻瀑布图（div+百分比宽度，色块区分 generation/tool/guardrail/confirmation/compaction，judge 裁决理由直接展示——"可解释"的主视觉）+ 概览卡片（token/成本/时间分解）。二期可选：聊天进行中经 CallbackSink 推 `TraceSpan` SSE 事件实时长出时间线（前端不认识的事件类型忽略，向后兼容）。

## 9. OTLP 导出（P4，可选 extra）

`milu[otel]` 提供 `OtlpSink`：内部 Span → OTel span 的单点映射（属性名已对齐，几乎只是格式转换），可发 Langfuse（`/api/public/otel`）/ LangSmith（`/otel`）/ Phoenix / Jaeger 任意后端。外发路径默认 `capture_content=none`（spec 要求 opt-in）。同期可选：`milu trace explain <id>`（LLM 生成自然语言运行复盘）。

## 10. 多用户与并发正确性

ContextVar 注入保证 asyncio 任务级隔离，AgentPool 并发运行各持独立 Tracer；trace.jsonl 跟随 session 目录 → (user, session) 天然隔离；runs.jsonl 带 user_id 字段，跨进程写入用 append（单行原子性与 scheduler outbox 同档取舍）；子代理经 ContextVar 继承父 trace 是期望行为（挂父树），子代理自身 `trace=False` 不影响继承。

## 13. 明确不做的事

- 不引入 OpenTelemetry SDK 为硬依赖（内核自有轻量模型，OTLP 仅 P4 可选 sink）；
- 不在 trace 中重复存完整对话（conversation.jsonl 已有，以 round 号互相关联；默认截断）；
