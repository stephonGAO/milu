# milu 沙箱执行后端 — 方案设计

> 为 `python_repl` / `shell_command` 提供**可插拔的执行隔离后端**，在既有「软门控」之上补齐「执行时隔离」。
> 代码位置：`src/milu/sandbox/`；接入点：`Agent(sandbox=...)` + `config.json` 的 `sandbox` 分节。

## 1. 背景与动机

milu 的两个代码执行工具在本方案之前是「名为沙箱、实为直跑」：

- **`python_repl`**：`exec(code, restricted_globals)` 跑在 **milu 自己的进程内**（线程池里），唯一限制是把 `open` 包了一层（拦截 milu 受保护路径）+ 一个软超时（默认 60s）。代码可 `import os/subprocess/socket`、读写任意非保护文件、发网络请求、吃满 CPU/内存；超时**杀不掉运行中的线程**（死循环泄漏线程）；进程内还能直接读 `os.environ` 拿到所有 `*_API_KEY`。
- **`shell_command`**：`asyncio.create_subprocess_shell` 直接在**宿主机** shell 上跑，权限 = milu 进程权限，仅靠正则黑名单（`rm -rf /`、`sudo`、…）+ 受保护路径检查兜底。

安全模型的主控是**操作模式 + AI 安全判定器**（talk/manual/auto/superwork + judge）——它决定**要不要执行**，但一旦放行，代码就在宿主机上裸跑，**没有任何 OS 级隔离**。这适合可信环境/单人本地，但不适合「不可信输入 / 多租户开放执行」。

本方案补齐执行时隔离这一层，且做到**可选分级、不强制人人装 Docker**。

## 2. 目标与非目标

**目标**

- 抽象一个**可插拔执行后端**，同一套工具按部署需要切换隔离强度。
- **库纯净**：裸 `Agent(llm)` 行为完全不变（默认仍是进程内/宿主直跑），`import milu` 零新增硬依赖，单测 hermetic。
- **复用既有机制**：配置走 `config.json` 新 `sandbox` 分节，注入走 `run()` 入口 ContextVar——与 knowledge/memory/tracer 同款，不发明新机制。

**非目标（本版本）**

- 不自研容器运行时。
- 不追求 Windows 上的完美隔离（子进程 + Job Object 为尽力而为）。
- Docker / 远程沙箱（E2B 等）为后续版本，本版本只把接口预留好。

## 3. 架构总览

```
src/milu/sandbox/
├── base.py      SandboxBackend(ABC) · ExecResult · _current_sandbox(ContextVar) · current_backend()
├── config.py    SandboxConfig(dataclass) · build_backend() 工厂
├── local.py     LocalBackend        进程内 exec / 宿主 shell（零依赖，可信场景的零开销档）
├── process.py   SubprocessBackend    独立子进程 + 资源限额 + 清洗环境 + guarded-open（跨平台零依赖，【默认】）
└── docker.py    DockerBackend        容器内执行（真隔离：断网/只读根/挂载工作区/限资源/用后即焚，走 docker CLI、零 Python 依赖；多用户/不可信输入首选）
```

**数据流**：`Agent.run()` 入口把后端实例 `set` 进 `_current_sandbox` ContextVar → 工具内 `current_backend()` 取到它（未注入则回退模块级 hermetic 后端 `LocalBackend`）→ `await backend.run_python/run_shell(...)` → 返回统一 `ExecResult` → 工具层格式化为回填 LLM 的文本。`ToolExecutor` 不感知沙箱，**执行器零改动**。

> **两个「默认」之别**：① **应用层默认**——`SandboxConfig.backend` 默认 = `subprocess`，经 `config.json` 驱动，CLI/Web 实际跑子进程隔离；② **hermetic 回退**——未经 Agent 注入时（裸工具调用 / 单测）`current_backend()` 恒回退 `LocalBackend`（进程内、零子进程开销），保证库纯净与测试速度。裸 `Agent(llm)`（`sandbox=None`）注入 `None` → 走 hermetic 回退 = local；只有应用层显式下传 `SandboxConfig` 才生效 subprocess。

### 接口

```python
@dataclass
class ExecResult:
    stdout: str = ""
    stderr: str = ""
    exit_code: int | None = 0   # 超时/无法获取时 None
    timed_out: bool = False

class SandboxBackend(ABC):
    name: str
    def __init__(self, config: SandboxConfig): ...
    async def run_python(self, code: str, *, timeout: int | None = None) -> ExecResult: ...
    async def run_shell(self, command: str, *, timeout: int | None = None) -> ExecResult: ...
    async def aclose(self) -> None: ...   # 容器/池清理，Local/Subprocess 为 no-op
```

`timeout` 是「本次调用」的覆盖值（`shell_command` 工具允许 LLM 传 `timeout`），为 None 时回退 `config.timeout`。

## 4. 三个后端与隔离强度

| 维度 | LocalBackend | SubprocessBackend（默认） | DockerBackend |
|---|---|---|---|
| python 执行 | 进程内 `exec` | 独立子进程 `python -X utf8 -I -` | 容器内 |
| 文件系统 | 全盘（除受保护路径） | 全盘（默认继承当前目录；guarded-open 拦受保护路径） | **完全隔离**（仅 tmpfs workdir） |
| 网络 | 不限 | 不隔离（本版本） | **`--network none` 默认断网** |
| 内存/CPU 限额 | 无 | `setrlimit`（内存硬限额仅 Linux 可靠；macOS 不强制、Win 跳过） | `--memory/--cpus/--pids-limit` |
| 超时能真杀进程 | ❌（线程泄漏） | ✅ kill 子进程 | ✅ kill 容器 |
| 密钥可见性（env 变量） | 进程内可读全部 `os.environ` | **env 清洗，看不到 `*_API_KEY`** | 完全隔离 |
| 密钥可见性（`.env` 文件） | guarded_open 拦截 | **guarded-open 拦截（已对齐 local）** | 完全隔离 |
| 改 milu 源码 | guarded_open 拦截 | **guarded-open 拦截（已对齐 local）** | 完全隔离 |
| 逃逸到宿主 | 容易 | 受限 | 极难 |
| 依赖 | 无 | 无 | 需装 Docker |
| 跨平台 | ✅ | ✅ | 需 Docker daemon |
| 定位 | 可信环境的零开销档 | **默认（综合最优：堵住 local 三缺口、编码工作流不变）** | 不可信输入/多租户开放执行 |

> **为何 subprocess 严格优于 local**：local 在进程内 `exec`，那三个缺口（能读 `os.environ` 全部密钥、软超时杀不掉死循环线程、崩溃波及主进程）是「同进程执行」的**固有属性**，无法在进程内补上——环境变量是进程级共享状态、Python 线程杀不掉、同进程同生共死。把代码放进**子进程**正是这三者唯一的修复手段。subprocess 再补两处使其不弱于 local：① guarded-open（堵 `.env` 文件读 / milu 源码写，与 local 对齐——否则「env 已清洗但 `.env` 仍可 `open` 读出密钥」会成旁路）；② 默认继承当前目录（编码工作流照常）。于是 subprocess = local 的全部防护 + 密钥/超时/崩溃三项硬提升。

### SubprocessBackend 实现要点（本版本核心，已加固为默认后端）

- **python 入口**：`[sys.executable, "-X", "utf8", "-I", "-"]`，代码经 **stdin** 喂入（避免命令行长度/转义问题）。
  - `-X utf8`：显式启用 UTF-8 模式。**不能依赖环境变量 `PYTHONUTF8`**——`-I` 含 `-E` 会忽略所有 `PYTHON*` 环境变量，故走命令行开关。
  - `-I`：隔离模式（忽略 `PYTHONPATH` / 用户站点、`sys.path[0]` 不含脚本目录）→ import 不到 milu 项目工作目录注入的源码。注意：用的是同一解释器的 venv，**已 pip install 的包仍可 import**（隔离的是「工作目录注入」，不是已安装包）。
- **guarded-open 注入（`_wrap_python`）**：执行前把用户代码包成「注入 `builtins.open` 守卫 → `exec(compile(code, '<repl>', 'exec'))`」的程序文本。受保护清单（目录/文件）由**父进程** `get_protected_paths()` 算好后以 `repr` 字面量注入（子进程 `-I` 隔离、不共享父状态；天然继承父进程 selfguard 开关，关闭则清单为空不拦截）。用 `compile('<repl>')` 而非把代码追加在守卫后，**保留用户代码异常行号从 1 开始**。⚠️ 这是「随手访问」防护，与 local 同档——determined 代码仍可经 `io.open`/`os.open` 等底层入口绕过；硬隔离请用 docker 后端。
- **环境清洗**：只透传 PATH + 系统必要项（Windows 的 `SystemRoot`/`COMSPEC` 缺了子进程起不来）+ 语言/编码变量，其余一律不传 → **执行的代码看不到 `{PROVIDER}_API_KEY` 等密钥**（local 进程内 exec 能直接读到，这是实打实的安全提升）。
- **资源限额（POSIX）**：`preexec_fn` 在 fork 后 exec 前调 `resource.setrlimit(RLIMIT_AS, ...)`（内存/地址空间）、`RLIMIT_CPU`（CPU 时间）。Windows 无 `preexec_fn`（需 Job Object，本版本不做），跳过。⚠️ **内存硬限额实际只在 Linux 可靠生效**——macOS 内核往往不强制 `RLIMIT_AS`（`setrlimit` 调用成功但不真正限制地址空间），需要内存隔离的多用户部署请用 docker 后端（`--memory`）。`RLIMIT_AS` 过低会让解释器/numpy 启动失败，默认 `memory_mb=1024`，且 `setrlimit` 容错（try/except），`None` 可关。
- **工作目录**：优先级 `固定 workdir > ephemeral 临时目录 > agent 工作区（current_workspace）> 进程 CWD`。即默认落在注入的 **agent 工作区**（`~/.milu/workspace`，与 `file_write` 落点一致，见「分层配置/工作区」），未注入工作区时回退进程 CWD（裸调用/单测的 hermetic 行为）；`ephemeral_workdir=True` 改为每次一次性临时目录（`tempfile.mkdtemp`，执行后清理，更强隔离）；显式配 `workdir` 则固定复用。
- **超时真杀**：`asyncio.wait_for(proc.communicate(...), timeout)` 超时即 `proc.kill()` + `await proc.wait()`，返回 `timed_out=True`。

## 5. 与现有安全模型的关系（正交）

三层叠加，互不替代：

| 层 | 职责 | 本方案是否改动 |
|---|---|---|
| 模式 + AI 判定（talk/manual/auto/superwork + judge） | 决定**要不要执行** | 不动 |
| 危险命令黑名单 + 受保护路径检查 | 后端无关的纵深防御，留在**工具层**，先于执行 | 不动（保留在 `shell_command`） |
| 沙箱后端 | 决定放行后**跑在哪、能碰什么** | 本方案新增 |

一句话：**门口照旧拦（要不要跑），新增的是把跑的地方关进笼子（怎么跑）**。

## 6. 配置与注入

### 配置（`config.json` 的 `sandbox` 分节）

默认值的唯一真相源是 `SandboxConfig` dataclass，分节经 `_builtin_defaults()` 从它派生（遵循「默认值只一份」铁律）：

```json
"sandbox": {
  "backend": "subprocess",   // local | subprocess | docker（默认子进程隔离）
  "timeout": 60,
  "memory_mb": 1024,         // 子进程地址空间上限 MB（POSIX RLIMIT_AS；null=不限）
  "cpu_seconds": null,       // 子进程 CPU 时间上限（POSIX RLIMIT_CPU；null=不限）
  "network": false,          // 仅 docker 生效；subprocess 本版本不隔离网络
  "max_output_chars": 8192,  // shell 输出截断上限
  "workdir": null,           // 固定工作目录（null=继承当前工作目录）
  "ephemeral_workdir": false,// true 时 subprocess 每次在一次性临时目录执行（更强隔离）
  "docker_image": "python:3.12-slim", // docker 镜像（首次执行按需自动拉取）
  "docker_cpus": null,                 // docker --cpus 配额（null=不限）
  "docker_user": null                  // docker --user（如 "1000:1000" 非 root；null=镜像默认）
}
```

**退回零开销本地执行**：`milu config set sandbox.backend local`（可信单人场景嫌子进程启动开销时）。**最强工作目录隔离**：`milu config set sandbox.ephemeral_workdir true`。

### 注入

- **构造**：`Agent(sandbox=...)`，与 knowledge 同款语义——`None`→不注入（工具回退 hermetic 后端 = LocalBackend）| `"local"` | `SandboxConfig` | `SandboxBackend` 实例。库纯净性：Agent 不读 `config.json`，由应用/CLI 入口读分层配置构造 `SandboxConfig` 下传。
- **运行**：`run()` 入口 `_current_sandbox.set(self._sandbox)`，`finally` 经 `_safe_reset` 重置——紧贴现有 `knowledge_token` 那批。子代理沿 ContextVar 继承父后端。
- **关闭**：`Agent.close_sandbox()`（`__aexit__` / AgentPool 淘汰路径调用），Local/Subprocess 为 no-op，为 docker 后端生命周期预留。
- **应用层**：CLI `build_agent` 与 Web `agent_factory` 读 `config.sandbox` → `SandboxConfig.from_mapping` → 传给 Agent。**默认 `subprocess`**（综合最优：堵住 local 三缺口，编码工作流不变）。注意「应用层默认 subprocess」与「hermetic 回退恒 local」是两个不同的默认（见 §3 注）。

## 9. Docker 后端（`docker.py`，本版本已实现）

真隔离档，**多用户 / 不可信输入首选**：容器内执行，宿主文件系统/网络/密钥都不可见。

- **每次执行一个一次性容器**：`docker run --rm -i --name milu_sbx_<uuid> --network none --read-only --tmpfs /tmp:rw --memory=<mb>m --memory-swap=<mb>m [--cpus] [--user] --pids-limit 512 -w /work <image> python -X utf8 -I -`，代码经 **stdin** 喂入；`run_shell` 走 `sh -c <command>`。
- **工作区挂载**：把 agent 工作区（`current_workspace()`）以 `-v {ws}:/work` 挂入并设为工作目录——**容器只看得见这一处宿主目录**，产物持久化到 `~/.milu/workspace/{user}`；无工作区时 `/work` 用 tmpfs（全隔离）。这正是「多用户安全」：每个用户的容器只挂自己的工作区。
- **不传宿主环境变量** → `*_API_KEY` 等密钥天然不可见（比 subprocess 的「清洗白名单」更彻底）；默认 `--network none` 断网（`network=true` 才放行）。
- **零硬依赖、可插拔**：只走 `docker` CLI 子进程，**不引入 docker Python SDK**——`pip install milu` 不需要任何额外包，`import milu.sandbox.docker` 也不依赖 docker 存在。仅当 `backend=docker` 且**真正执行**时才需要本机 Docker Engine。
- **懒探测 + 按需拉镜像**（`_prepare`，结果缓存）：首次执行才 `docker version` 探测 daemon、`docker image inspect`/`docker pull` 确保镜像就绪。未安装 / daemon 未启 / 拉取失败 → 返回**中文友好错**（提示改用 subprocess），不抛异常、不崩对话。
- **超时真杀**：`--name` + 超时 `docker kill <name>`（`--rm` 随后清理容器）。
- 容器生命周期用 per-call `--rm` 临时容器（最简、最安全）；容器池化降启动延迟为后续优化（P3）。
- 注意：容器内是镜像自带的 Python/包（默认 `python:3.12-slim`），不是 milu 的 venv，故 `import milu`/第三方库需镜像内已有。`docker_mounts` 可 opt-in 额外挂载，`docker_user` 可设非 root（Linux 挂载属主权衡）。
